# 新设备接入

适用于「买了个模块，帮我接上」或「把这个已有硬件项目登记进来」。目标是完成用户需要的最小可用功能，再留下可复用的命令和说明书。

## 1. 判断接入起点

| 已有条件 | 从哪里开始 |
|---|---|
| 已有能用的固件和 CLI | 核对项目、只读验证，直接进入登记与交付 |
| 有项目，但缺少用户需要的功能 | 沿用项目，结合[扩展指南](extension-guide.md)补齐 |
| 只有硬件、没有项目 | 确认需求与接线，选择工具链并开发 |
| 暂时没有硬件或缺少关键材料 | 完成代码、模拟测试或方案，明确待实机验证的部分 |

不要因为设备尚未登记就重写一个已有可用项目。

## 2. 一轮问清必要信息

使用当前环境可用的问答工具；没有工具就用简短编号列表。只问仍未知、会影响实现的问题，创意工坊中已回答的信息直接复用。

| 信息 | 问法示例 |
|---|---|
| 设备与主控 | 模块型号、开发板型号或商品链接是什么？ |
| 最小目标 | 想先读取数值、显示内容、控制动作，还是做联动？ |
| 使用方式 | 桌面通过 USB 控制、局域网远程，还是需要蓝牙？ |
| 材料与现状 | 已有项目、接线、电源、驱动板和连接线有哪些？ |

用户没有偏好时，按目标选择：桌面首次联调可优先 USB；需要局域网远程再选 WiFi；移动端或低功耗场景再评估 BLE。说明选择理由，不把 WiFi 当成所有模块的默认能力。

## 3. 确认资料、项目与工具链

- 优先已有资料、厂家数据表和当前开发板 pinout；区分开发板型号与芯片型号，同一芯片的不同模组也可能占用不同引脚。
- 型号、供电或引脚不清楚时先取得资料。已确认接口和电压后可以做有依据的只读探测；连续失败且没有新的线索时记录已排除项，说明缺少什么。
- 用户已有偏好或项目配置时沿用：`platformio.ini` → PlatformIO；ESP-IDF 的 CMake/sdkconfig → ESP-IDF；`.ino` → Arduino；MicroPython/CircuitPython 按对应文件部署方式；Linux 单板机沿用现有 Python 环境。

新项目按需求选择：

| 场景 | 候选工具链 | 选择依据 |
|---|---|---|
| ESP32 与常见传感器、灯板 | Arduino / PlatformIO | 可复用较多现成库 |
| ESP32 的底层功能、低功耗或复杂外设 | ESP-IDF | 官方驱动与配置能力 |
| 教学、快速修改脚本 | MicroPython / CircuitPython | 板型支持和模块驱动可用性 |
| 树莓派等 Linux 单板机 | Python + 对应 GPIO/I2C 库 | 已有系统接口与权限 |
| 其他主控 | 厂家推荐环境 | 数据表与官方示例 |

检查实际编译工具是否可用，按任务需要配置缺少的依赖，并记录使用的版本。项目目录包含用户代码时先检查再修改，不用模板覆盖整个目录。

## 4. 接线与独立准备

给出明确的引脚表或 ASCII 图，标注电源来源、信号方向和本次需要的共地关系。选择 GPIO 时核对启动脚、USB、Flash/PSRAM 与板载外设占用。

提醒先断电再接线；电压以模块资料为准，电机使用匹配的驱动与保护电路，舵机和大灯带按最大电流安排供电。只提示与这次接线有关的事项。

等用户确认接好后再进行通电测试。等待期间可继续编写代码、准备模拟传输测试和说明书；不要盲目拉高未知引脚。

## 5. 开发可验证的最小功能

遵循项目架构与[协议参考](protocol-template.md)，先定义用户需要的命令及只读 `status`，再实现固件、通信库和 CLI。并非每个项目都需要完整重建三层代码，例如已有库或 Linux GPIO 项目可以复用原入口。

- 参数、范围、默认值和错误码在 CLI、通信库、固件之间保持一致；错误参数在触发动作之前返回。
- TCP、串口和 BLE 按各自的分帧方式实现有界缓冲和超时。调试日志与数据响应分离，避免客户端把日志当成响应。
- IP / 端口缓存只在成功通信后更新。WiFi 凭据放项目中被 Git 忽略的私有配置；缺少时提供本地配置入口，无需用户把密码贴进公开文档。
- 需要演示脚本时只编排已经验证的功能，明确持续时间与停止方式。停止 PC 脚本不一定停止设备动作，停止命令必须由驱动实际支持。

## 6. 分层验证

1. **软件检查**：编译或语法检查；参数错误、消息分帧、超时等使用模拟传输验证。
2. **上传与连接**：按 SKILL.md 的固件流程核对板型和端口，上传后读取有时限的日志或调用只读查询。
3. **目标动作**：在工作条件明确后验证用户需要的功能，记录真实响应。运动、加热等设备不为了“跑全命令”触发无关动作。
4. **实物反馈**：仅让用户观察软件无法确认的结果；未获得确认时将其列为待验证项。

编译失败先处理首个有效错误；通信失败进入[排障指南](troubleshooting.md)。没有实机时仍可交付已完成的软件与检查结果，明确下一次连接设备后从哪一步继续。

## 7. 登记与交付

按[注册表指南](registry-guide.md)更新设备：

- `name` 与别名唯一；保留其他设备和已有扩展字段。
- `project_path`、CLI、库和说明书路径真实可解析；记录实际 transport、板型、工具链和引脚。
- 每条命令填写 `desc`、`argv`、结构化 `args`、幂等性、只读性与超时。需要在控制时覆盖的 IP / 串口也要有明确参数入口。
- 使用 `register --file` 登记单台设备；已有设备先 `show`，再带返回的 revision 调用 `update --file`。工具负责校验、保留其他数据、备份和原子写入，用 `plan` 检查代表性命令。

根据[说明书指南](delivery-doc-guide.md)生成或更新项目文档并打开。收尾说明设备实现了什么、两三个可以直接说的指令、文档位置，以及已验证和待验证的范围。
