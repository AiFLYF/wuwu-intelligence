# 通信协议参考：单行 JSON 与非阻塞处理

用于新设备协议设计。具体驱动需按硬件项目实现并验证；本仓库不包含可直接烧录的通用固件。

## 消息与参数

1. 请求和响应使用 UTF-8 JSON，以 `\n` 分帧，可兼容 `\r\n`。请求必须是对象，含字符串 `cmd`。
2. 每条请求恰好对应一个响应。成功为 `{"ok":true,...}`，失败为 `{"ok":false,"code":"E_ARG","error":"简短说明"}`。
3. 新协议建议携带 `id`，响应原样回传；客户端核对请求与响应，避免迟到响应被下一条命令误用。旧设备是否支持该字段必须实测。
4. 只有明确声明的可选参数使用默认值。必填参数缺失、类型错误或越界返回 `E_ARG`，在产生设备动作之前完成全部校验。
5. 提供不改变设备状态的 `status`，返回当前模式、关键参数、连接信息与运行时长；响应成功不等于已经确认实物效果。

```json
{"id":"42","cmd":"color","r":255,"g":0,"b":0}
{"id":"42","ok":true,"mode":"solid"}
```

## 错误与重试

| code | 含义 | 客户端行为 |
|---|---|---|
| `E_CMD` | 不支持的指令 | 报告能力缺失，不原样重试 |
| `E_ARG` | 参数缺失、越界或类型错误 | 修正参数，不原样重试 |
| `E_BUSY` | 当前不能接收动作 | 明确请求未执行且重试安全时，稍后最多重试一次 |
| `E_HW` | 外设初始化或运行失败 | 只读诊断后排查接线、供电和外设 |
| `E_TIMEOUT` | 设备内部等待超时 | 结果可能未知，先查询状态，不盲目重发动作 |
| `E_JSON` | 请求或响应不是约定的合法 JSON | 检查分帧、编码、日志混入与协议兼容性 |

通信库保留 `code` 和原始诊断上下文，CLI 返回非零退出码并给出用户能理解的信息。无有效响应的传输超时要与设备返回的 `E_TIMEOUT` 区分。

**重试由命令语义决定。** 设置绝对颜色通常可安全重复，增量移动、投料、开锁、一次性演示序列通常不可。连接断开或响应丢失不代表动作没有执行；需要自动重试的非幂等动作必须先实现并验证服务端请求去重。

## 传输方式

| 方式 | 注册表示例 | 实现要点 |
|---|---|---|
| WiFi TCP | `tcp:8888` | `socket` 接收流，处理分包与粘包，不把一次 recv 当作完整消息 |
| USB 串口 | `serial:COM7@115200` | `pyserial` + 有上限的读超时；固件逐字节累积到换行 |
| BLE | `ble:设备名` | 例如 NUS + `bleak`；按协商 MTU 分片，按消息分帧重组通知 |

每个连接维护独立缓冲区。按最大有效负载设置行长上限（例如 4096 字节），超过上限、读超时或收到不完整行时清理/关闭连接并报告；不能无限增长内存或无限等待。

数据通道不要混入任意调试文本。优先分离日志通道；必须共用时定义可识别的日志消息，并在客户端实现有界过滤。不能简单把第一行当成响应。

## 固件主循环

```text
loop:
    maintainLink()       # 根据时间戳推进连接/退避，不阻塞主循环
    readAvailable()      # 有界缓冲，凑齐一行后解析
    validateAndDispatch() # 检查 cmd 与参数，再调用动作
    updateDevice()      # 用时钟推进动画、传感器或运动状态
```

- Arduino 可使用 ArduinoJson；按项目固定并记录库版本。
- 用统一分发器发送一次响应，避免命令函数和分发器双发。
- 不用 `readStringUntil()`、长 `delay()` 或循环等待阻塞动画与输入处理。
- WiFi 重连按板型、功耗需求和现场网络设计退避；不要把某个灯板项目的重连参数当成所有设备的要求。
- USB 日志采集应有时限，采集结束关闭端口，不持续占用烧录接口。

## PC 端

通信库提供连接生命周期、按行收发和语义方法；CLI 使用子命令，参数校验与固件保持一致。缓存的 IP / 串口只在成功通信后更新到本地配置。

先用模拟传输测试分包、粘包、超长行、非法 JSON、迟到响应和超时，再做实机验证。编译或语法检查只能证明代码可构建，不能代替这些行为测试。
