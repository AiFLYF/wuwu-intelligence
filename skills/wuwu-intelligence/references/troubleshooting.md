# 硬件排障指南

先使用用户提供的错误、设备档案、只读查询和有时限的日志缩小范围，再选择下面的分支。不要一开始就要求用户逐项尝试整张清单，也不用一个控制动作代替诊断。

## 1. 先区分错误来自哪里

| 证据 | 优先检查 |
|---|---|
| 注册表校验失败、CLI 尚未启动 | [注册表指南](registry-guide.md)中的格式、参数、路径或旧格式迁移 |
| `E_CONFLICT` | 重新读取设备快照并比较改动；不要删除锁文件或强行覆盖较新的内容 |
| 程序启动失败、模块导入错误 | Python/工具链环境、依赖和实际工作目录 |
| 收到协议错误码 | 参数与设备状态，不先把问题归因于网络 |
| 连接超时、拒绝连接或无响应 | 按 transport 选择 TCP / 串口 / BLE 分支 |
| 命令有有效反馈，但实物表现不对 | 接线、供电、布局与具体驱动配置 |

错误语义与[协议参考](protocol-template.md)保持一致：

| code | 下一步 |
|---|---|
| `E_CMD` | 设备或当前固件没有该指令；核对版本与已登记能力 |
| `E_ARG` | 对照 `args` 修正类型、范围或缺失参数，不原样重试 |
| `E_BUSY` | 确认请求未执行且可安全重复时，可稍后重试一次 |
| `E_HW` | 只读诊断后检查相应外设、接线和供电 |
| `E_TIMEOUT` | 执行结果可能未知，先查状态，不重发未知结果的动作 |
| `E_JSON` | 检查消息分帧、编码、日志混入和协议版本 |

只对原因明确、可安全重复的命令考虑一次重试。增量移动、投料等动作的响应丢失，不能解释成“动作没执行”。

## 2. 连接问题

### TCP

1. 从设备实际配置取得地址和端口。只有用户提供或真实日志得到的新地址才能更新缓存，不能猜测后覆盖。
2. 检查目标服务端口。`connection refused` 通常说明服务未监听或端口不对；timeout 还可能涉及离线、路由、隔离或防火墙。
3. ping 只作为辅助证据：不通可能是 ICMP 被禁，不能单凭它认定设备断电；通了也不能证明目标服务正常。
4. 有可用串口日志时确认网络连接与服务器启动信息；只有供电或指示灯等无法从软件确认时才请用户观察。

手机热点、访客网络或 AP 隔离场景需要核对设备间通信能力。重连策略以实际固件实现为准，不假定已自带某套重试次数。

### USB 串口

- **打不开**：检查端口是否还对应原设备、USB 驱动是否可用，以及是否被监视器或其他程序占用。
- **打开无响应**：核对固件的实际波特率、换行、协议与启动时序。115200 只是常见示例，不是固定要求。
- **打开后设备重启**：部分开发板受 DTR/RTS 影响会自动复位；核对库的端口设置，不反复开关正在执行关键任务的设备。
- 日志采集设置时间上限并及时关闭端口；不要为了查看日志长期阻塞后续烧录。

### BLE

- 扫描不到：检查是否在广播、服务 UUID/地址是否正确，以及操作系统蓝牙权限。
- 已连接但无数据：检查特征 UUID、通知订阅、写入方式和 MTU 分片。
- 已有其他客户端连接：确认该设备支持的并发连接数；不要把所有 BLE 设备都当成固定一对一。
- 距离、干扰或适配器驱动可作为后续排查方向，需要结合实际断开原因判断。

## 3. WiFi 日志

先确认日志来自哪套框架和固件版本。Arduino WiFi 的常见状态值仅作定位示例：`1` 常表示找不到 SSID，`3` 表示已连接，`4` 表示连接失败，`6` 表示未连接；其他框架应查对应定义。

核对具体芯片支持的频段、SSID、信号、认证方式和 DHCP。连接失败不一定是密码错误；也不要在没有证据时升级全部依赖或改动路由器配置。需要固件重连时采用有上限的非阻塞退避，保留现有功能。

## 4. 灯板、供电与图案问题

以下主要针对 WS2812 一类灯板，其他模块按其资料处理。让用户动线前先断电。

| 现象 | 重点核对 |
|---|---|
| 完全不亮 | 模块规定电压、GND、数据方向 IN/OUT、实际 GPIO 与驱动初始化 |
| 乱闪、局部失真 | 信号地、供电稳定性、电平匹配与信号线；电阻、电容按器件建议配置 |
| 低亮度正常、高亮度闪 | 电源额定电流、压降和连接线；按具体灯珠数据表估算最大负载并留余量 |
| 红绿或其他颜色互换 | 固件配置的 RGB / GRB 等色序 |
| 图案镜像或走向不对 | 行列方向、起点和蛇形布局；使用项目实际的布局配置 |

每珠约 60mA、64 珠约 3.8A 是部分旧型号全白时的估算，不能直接套用到所有 LED 型号。

## 5. 编译与烧录

- **Arduino / PlatformIO**：先看首个有效错误，核对板型、FQBN、框架、库版本和代码使用的 API。缺依赖时按项目配置补齐，不把升级所有库作为默认修复。
- **ESP-IDF**：使用当前系统对应的环境入口，核对 target 与真实芯片。只有证据指向缓存问题时清理构建；修改 target 或 sdkconfig 前保留用户配置。
- **MicroPython / CircuitPython**：核对固件构建是否包含所需模块、库文件是否已部署，以及 REPL 是否被占用。
- **容量不足**：检查当前芯片容量与分区需求。改变分区可能影响 OTA 或已有数据，不能一律切成某个“大应用”模板。
- **下载模式失败**：按具体开发板官方流程进入下载模式，核对 USB 线、驱动和端口身份；不要给所有板型套同一套 BOOT/RST 步骤。

## 6. 卡顿或指令迟迟不返回

检查输入读取、动画、传感器等待和网络重连是否阻塞主循环；按实际负载控制刷新频率。通信库应处理分包、粘包和迟到响应，并限制消息缓冲长度。

向用户汇报已证实的原因、做了什么，以及下一步。暂时无法确认时明确缺少哪条证据；避免用“现在连接成功”替代“实物已恢复”的结论。
